# 04 · 登录与凭据处理设计（方案讨论，未实现）

> 状态：**设计稿**（2026-11-03）。只讨论方案，不含代码实现。
> 背景：P3 需要登录态；当前唯一路径是"用户自己在浏览器登录 → 导出 cookie 给 agent"，体验上多此一举。
> 但若让 agent 参与密码/短信，秘密会进入会话记录与模型上下文。本文给出拆分方案与推荐路线。

---

## 1. 问题定义

P3（`serve` + CDP）能带 cookie 抓数据，但**cookie 从哪来**没有闭环：

| 现状 | 问题 |
|---|---|
| 用户自己浏览器登录 → 导出 storageState/cookies → 交给 agent | 多此一举；且文件可能被贴进聊天 |
| 让 agent 填账号密码 | 密码进入 `session.v4.jsonl.zstd` / 模型上下文 / 日志，永久留存 |
| 让 agent 接收短信验证码 | 同上；验证码短期有效但同样敏感 |
| 让 agent 过图形/滑块验证码 | lightpanda 无视觉、无布局引擎，**做不到**；且属绕过安全机制 |

**核心矛盾**：登录必须发生，但秘密不能进入 agent 这一侧。

---

## 2. 设计原则（硬约束）

1. **秘密不进 agent 上下文**：密码、短信码、cookie 值都不应出现在模型输入/输出、工具输出、会话记录里。
2. **agent 只拿"能力"不拿"秘密"**：agent 得到的是 `cookie 文件路径 / session id / 状态`，不是凭据值。
3. **秘密由本地可信组件持有**：一个在会话之外运行的 helper（独立终端/窗口/本地页面）负责用户输入。
4. **扫码优先**：二维码不是秘密（是临时授权），是唯一"agent 可参与"的登录方式；其余方式必须 out-of-band。
5. **不做验证码识别/绕过**：遇到 captcha 就失败并如实报告，交人工处理。
6. **cookie 按 bearer token 对待**：等同于密码级别，600 权限、不打印、可撤销、有有效期。

---

## 3. 威胁模型

| 在保护范围内 | 不在范围内 |
|---|---|
| 会话记录持久化（`session.v4.jsonl.zstd`） | 本机 root / 同用户恶意进程 |
| 模型上下文与工具输出 | 站点服务端自身泄露 |
| 日志与诊断包（分享前需脱敏） | 用户主动把秘密贴进聊天（只能提示，无法阻止） |
| 多人共用设备的文件读取 | 网络侧中间人（TLS 由 libcurl/系统 CA 负责） |
| 二维码钓鱼（把攻击者的码给用户扫） | 站点风控识别自动化（无法消除，见 SKILL 已知限制） |

---

## 4. 候选方案对比

| 方案 | 秘密是否进 agent | 体验 | 安全 | 工程量 | 适用 |
|---|---|---|---|---|---|
| **A. 本地登录助手**（独立终端/窗口输入） | ❌ 不进 | 好（一次命令） | 高 | 中 | 密码 / 短信 |
| **B. 系统钥匙串**（Keychain/凭据管理器/secret-service） | ❌ 不进 | 最好（首次录入，之后一键） | 最高 | 中高（跨平台差异） | 密码（长期复用） |
| **C. 扫码** | ❌ 不进（二维码是临时授权） | 最好 | 高（需防钓鱼码） | 低 | 支持扫码的站点 |
| **D. 凭据代理守护进程**（本地服务 + 自有登录页） | ❌ 不进 | 好（多会话/多任务） | 高（但攻击面变大） | 高 | 长期多站点 |
| **E. 手工导出 cookie**（现状） | ❌ 不进 | 差（多此一举） | 中（文件易被贴进聊天） | 无 | 兜底 |

**评分（安全/体验/成本）**：C ≈ B > A > D > E（按"先能落地"排序：**C → A → B → D**）。

---

## 5. 推荐架构

```
                 ┌───────────────────────────── agent 会话（模型上下文/记录）────────────────────┐
                 │  login.mjs <site>                （只得到状态 JSON / cookie 文件路径）         │
                 └───────────────┬────────────────────────────────────────────────────────────┘
                                 │ 启动（stdio 不经过 agent）
                                 ▼
        ┌────────────────────────────────────────────────────────────┐
        │ 本地 helper（独立 TTY / 本地窗口 / 127.0.0.1 页面）           │
        │  · 展示二维码（打印目标域名，防钓鱼）                        │
        │  · 接收用户输入的密码 / 短信码（不回显、不落盘、不进日志）     │
        └───────────────┬────────────────────────────────────────────┘
                        │ 通过 127.0.0.1 CDP 驱动
                        ▼
        ┌──────────────────────────────────────────────┐
        │ lightpanda serve（P3，仅监听 127.0.0.1）       │
        └───────────────┬──────────────────────────────┘
                        ▼
        ~/.config/dsh-lightpanda/sessions/<domain>.json   （cookie jar，chmod 600）
```

关键点：
- **helper 与 agent 的 stdio 隔离**：agent `spawn` helper 时 `stdio: 'ignore'`，helper 自己开终端窗口/本地页面与用户交互；agent 只轮询"状态文件 / exit code"。
- **cookie 文件是唯一交付物**：P3 `serve --session <domain>` 自动加载，退出时回写；过期自动提示重新 login。
- **agent 永远不读 cookie 内容**（只传路径）；SKILL 明确禁止打印 cookie。

## 6. 接口草案

### 6.1 `login.mjs`

```sh
node scripts/login.mjs <url|site>            # 自动选择方式（有二维码则 QR）
  [--method auto|qr|password|sms]
  [--account <name>]                          # 同域名多账号
  [--timeout 180]                             # 秒
  [--out ~/.config/dsh-lightpanda/sessions/<domain>.json]
  [--no-open]                                 # 不自动开 helper 窗口（调试用）
```

输出（stdout，JSON，**不含秘密**）：

```jsonc
{ "status": "needs_scan",  "domain": "search.bilibili.com",
  "qrFile": "~/.config/dsh-lightpanda/qr/bilibili-1730000000.png",
  "hint": "请用手机扫码（确认域名后再扫）" }
{ "status": "needs_password", "helper": "tty", "hint": "请在弹出的终端窗口输入" }
{ "status": "needs_code", "channel": "sms", "expiresIn": 120 }
{ "status": "ok", "cookieFile": "~/.config/dsh-lightpanda/sessions/bilibili.json", "expiresAt": 1799999999 }
{ "status": "expired" } / { "status": "blocked", "reason": "captcha" } / { "status": "failed", "reason": "..." }
```

### 6.2 会话管理

```sh
node scripts/sessions.mjs list                 # 域名 / 账号 / 过期时间 / 文件大小
node scripts/sessions.mjs show <domain>        # 只显示元信息（不显示 cookie 值）
node scripts/sessions.mjs rm <domain>          # 删除（撤销本地会话）
```

### 6.3 P3 集成

```sh
node scripts/serve.mjs ensure --port 9223 --session bilibili
#   → 自动加载 sessions/bilibili.json；退出/stop 时回写 cookie-jar
#   → 过期检测：加载时校验 expires，过期提示跑 login
```

目录布局：

```
~/.config/dsh-lightpanda/
  sessions/<domain>[@account].json     # 600
  qr/<domain>-<ts>.png                 # 临时，扫完即删
  login.log                            # 无秘密审计：时间/站点/方式/结果/耗时
```

## 7. 三种方式的状态机

### 7.1 扫码（C，推荐先做）

```
打开登录页 → 找二维码元素
  ├─ <img src="data:image/..."> → 直接解码落盘（B站/头条常见）
  ├─ 页面 canvas 绘制二维码 → ❌ 不支持（lightpanda 无 canvas），改为提示人工
  └─ 找不到 → 报告 blocked，建议换密码方式
→ 打印「目标域名 + 二维码路径」（防钓鱼：域名必须与 --url 的主域一致）
→ 用户扫码授权
→ 轮询判定：URL 离开登录页 / 关键 cookie 出现 / localStorage 标记
→ 写 session 文件（600）→ 清理二维码
超时（默认 180s）→ 清理 → status=expired
```

### 7.2 密码（A/H，秘密只在 helper）

```
helper 窗口：提示「输入 <域名> 的账号/密码」（不回显）
→ 通过 CDP 填表：优先 Input.insertText/点击（真实事件），必要时 evaluate
→ 提交 → 检测成功/失败
→ 失败：有限次重试（≤3），递增等待；仍失败 → failed（不猜测）
→ 成功后：若站点要求短信 → 转 7.3；否则写 session
注意：密码只在 helper 进程内存中存活，不写盘、不进日志、不经过 agent stdio
```

### 7.3 短信/OTP（A）

```
提交密码后页面出现验证码输入框
→ helper 提示「输入短信验证码（120s）」；显示"重新发送"按钮逻辑
→ 用户输入 → 填入 → 提交
→ 超时/错误 → 允许重发 1 次；仍失败 → failed（如实报告）
```

### 7.4 失败与风控

- 检测到 captcha/滑块/`bot_challenge` → **立即失败**，不尝试绕过，输出 `blocked`。
- 账号被锁/需要设备确认（如微信/QQ 授权）→ `needs_user`，提示人工在手机完成。
- 任何情况下不记录密码、验证码、完整 cookie。

## 8. 安全要求清单（实现时必须满足）

- [ ] 目录 `~/.config/dsh-lightpanda/` 700、session 文件 600；启动时检查并纠正权限。
- [ ] helper 输入不回显（TTY 关闭 echo）；不写 shell history；不写临时明文文件。
- [ ] agent 侧禁止打印 cookie 值；`sessions show` 只给元信息。
- [ ] 日志/审计不含秘密；分享诊断包前自动脱敏（复用现有脱敏规范）。
- [ ] 二维码防钓鱼：展示域名；二维码归属与请求 URL 主域不一致时拒绝显示。
- [ ] cookie 过期/撤销检测；不同域名/账号隔离，不跨域复用。
- [ ] 登录失败限速（≤3 次，指数退避），避免触发站点风控。
- [ ] 只监听 127.0.0.1；helper 不监听公网；关闭 telemetry。
- [ ] 明确文案：agent 不索要密码/验证码；用户若粘贴，提示丢弃并改用 helper。

每阶段都要有"秘密不进会话"的验证：`zstd -d session.v4.jsonl.zstd | grep -c <test-secret>` 必须为 0。

## 10. 待你决策的问题

1. 密码类站点：愿意存 **系统钥匙串**（B）吗？还是每次登录在 helper 里手动输（A）？
2. 能接受 helper **另开一个终端窗口 / 本地页面**吗？（这是"秘密不进 agent"的关键）
3. session 文件要不要**再加一层口令加密**（例如 age/gpg）？会牺牲"一键自动加载"。
4. 是否需要**多账号**（同站点 A/B 号）？影响目录与 `--account` 设计。
5. 优先支持哪些站点？（建议先 B 站/头条扫码，再挑一个密码站验证）

## 11. 明确不做

- 验证码识别、滑块破解、短信轰炸/接码平台。
- 批量账号矩阵、绕过风控、爬取他人私密数据。
- 把密码/验证码写进任何日志、session、报告或示例。
- 把 helper 暴露到公网。
