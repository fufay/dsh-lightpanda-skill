# 03 · 设计与发布

## 1. 结构

```
skill/dsh-lightpanda/
  SKILL.md                 # agent 读的执行手册（P2/P3、路由、判定、安全）
  scripts/resolve.mjs      # 平台探测 + 下载/校验/缓存（多镜像，sha256）
  scripts/fetch.mjs        # P2：调 fetch（默认 markdown，wait/cookie/robots 等）
  scripts/serve.mjs        # P3：serve 生命周期（start/ensure/stop/status/restart）
  scripts/cdp.mjs          # 零依赖 CDP：navigate/poll-selector/eval，输出 JSON
  assets/manifest.json     # 平台→资产、sha256、镜像地址、tag
tools/install.sh           # 复制 skill 到 DSH skills 目录
tools/publish-release.sh   # GitHub + AtomGit 发布（--github-only/--atomgit-only）
tools/atomgit_release.py   # AtomGit API：建 release + 签名两步上传
```

## 2. 平台解析（resolve.mjs）

| 运行环境 | 选择资产 |
|---|---|
| `process.platform = openharmony`（Whale/OHOS） | `lightpanda-aarch64-ohos`（静态自签） |
| linux + arm64/aarch64 | 同上（静态，glibc/musl 通吃） |
| linux + x64 | `lightpanda-x86_64-linux`（glibc） |
| darwin + arm64/x64 | 对应 macOS 资产 |
| win32 | 报错并提示 WSL2（上游无原生 exe） |

缓存：`~/.cache/dsh-lightpanda/<tag>/lightpanda`；下载后校验 manifest 的 sha256，不匹配即换镜像。
镜像顺序：`DSH_LIGHTPANDA_ASSET_BASE`（自建）→ **AtomGit** → **GitHub** → 上游 nightly。
离线：`DSH_LIGHTPANDA_LOCAL_DIR=<dir>` 直接从本地拷贝（仍校验 sha256）。

## 3. 发布流程

前提：`gh auth status` 正常；`ATOMGIT_TOKEN`（或 `ATOMGIT_TOKEN_FILE`）为 AtomGit 私人令牌。

```sh
# 1) 本地提交并推到两个远端
git push https://github.com/fufay/dsh-lightpanda-skill.git HEAD:refs/heads/main
git push "https://Kevin911:<token>@atomgit.com/Kevin911/dsh-lightpanda-skill.git" HEAD:refs/heads/main

# 2) GitHub 发行（需要代理时用 with-proxy.sh 包一层）
sh Common/ProxyAgent/scripts/with-proxy.sh sh tools/publish-release.sh --tag <tag> --github-only

# 3) AtomGit 发行（国内直连）
sh tools/publish-release.sh --tag <tag> --atomgit-only

# 4) 验证（两个源都要能下）
curl -sI "https://atomgit.com/Kevin911/dsh-lightpanda-skill/releases/download/<tag>/manifest.json"
curl -sIL "https://github.com/fufay/dsh-lightpanda-skill/releases/download/<tag>/manifest.json"
```

### AtomGit API 要点（已实测）

- 基址 `https://api.atomgit.com/api/v5`；认证头 **`PRIVATE-TOKEN`**（不是 `Authorization: token`）。
- 建 release：`POST /repos/{owner}/{repo}/releases`，body `{tag_name,target_commitish,name,body}`。
- **release 对象没有 `id`**，后续一律用 `tag` 定位。
- 附件上传是**对象存储签名两步法**：`GET .../releases/{tag}/upload_url?file_name=<f>` → 拿到 `url` + `headers` → `PUT` 文件，**必须原样带返回的 headers**（`x-obs-*`）。
- **不支持同名附件覆盖**：发新版必须换 tag/文件名。

## 4. 升级上游（nightly 变了怎么办）

```sh
# 1) 重新下载 4 个上游资产（与本仓库 _build/assets 同布局）
# 2) 重新生成 manifest（sha256/size/时间）
# 3) 改 manifest.release_tag 为新 tag，提交
# 4) 按 §3 发新 tag
```
OHOS 资产（`lightpanda-aarch64-ohos`）来自 `Eva-Research/2026-11-02-lightpanda-评估` 的 `tools/build-lightpanda.sh`；
上游升级后需先在那里重编，再拷到 `_build/assets/`。
