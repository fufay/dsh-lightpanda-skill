# 03 · 原生代码与签名（.codesign / ELF 加载）

> **仅原生项目需要**（C/C++/NDK/自编 `.so`）。非原生项目可忽略本文件。
> 本机工具现状已于 2026-10-23 核实；**路线 B（self-sign）已在 `mc-runtime-lab` 项目验证成功**（E2），路线 A 工具存在但未实测。

## 1. 现象：dlopen / mmap(PROT_EXEC) 被拒

HarmonyOS 对可执行内存加载有校验。自编 `.so` 若**缺少 `.codesign` 段**，常见表现为：
`dlopen` 失败或 `mmap(PROT_EXEC)` 被拒 —— **`.codesign` 段缺失就是最直接的物证**。

```sh
readelf -S libfoo.so | grep -i codesign     # 有 .codesign 才可能被放行
```

## 2. 本机已核实的工具

| 工具 | 路径（已核实存在） | 说明 |
|---|---|---|
| `ld.lld` | 官方：`<hmos-clt>/sdk/default/openharmony/native/llvm/bin/ld.lld`；`<hmos-clt>/sdk/default/hms/native/BiSheng/bin/ld.lld`；brew `~/.harmonybrew/Cellar/ohos-sdk/…/bin/ld.lld`（legacy） | LLD 15.0.4；`--help` 含 `--code-sign`（Code self sign when enable）、`--no-code-sign`（默认不带签名）；BiSheng 版另有 `--linker-code-sign` |
| `binary-sign-tool` | **官方优先** `<hmos-clt>/sdk/default/openharmony/toolchains/lib/binary-sign-tool`；brew ohos-sdk 同名工具仅 legacy fallback | 子命令 `sign` / `display-sign`；`sign` 参数含 `-inFile`（ELF）、`-appCertFile`、`-profileFile`、`-keyAlias`、`-keyPwd` |
| `readelf` | PATH 可用（`$HOME/bin/readelf`） | 查 `.codesign` 段 |

`display-sign` 实测（对无签名的系统库）：
```
permission is not found
code signature is not found
```

> ⚠️ 系统库（如 `/system/lib64/libc.so`）可以**没有** `.codesign` 也正常工作；
> 不能仅凭"段缺失"就判定失败 —— 必须用**自己编的 .so + dlopen 实测**复现。

## 3. 两条路线

> 🔎 **本机实测（2026-10-23）**：用 brew clang 链接的 `.so` **默认就带 self-sign `.codesign`**
> （`display-sign` 输出 `code signature is self-sign`）。⇒ **自己编的库通常无需补签**；
> 真正需要 `binary-sign-tool -selfSign 1` 补签的是**下载来的第三方 .so**（如 libjvm）。
> 显式控制可加 `-Wl,--code-sign` / `-Wl,--no-code-sign`。

**路线 A（链接期自动签名，工具存在但未实测）**：编译/链接时打开 code-sign：

```sh
clang ... -Wl,--code-sign          # 或直接调 ld.lld 时加 --code-sign
# 本机 ld.lld 已确认支持 --code-sign（LLD 15.0.4），但尚无项目实测数据
```

**路线 B（后处理 self-sign，✅ 已在 `Common/mc-runtime-lab` 项目验证 → E2）**：

```sh
# 目标库 + **全部依赖**逐个 self-sign（注意：不是 app 签名！）
binary-sign-tool sign -inFile libjvm.so         -outFile libjvm_selfsign.so         -selfSign 1
binary-sign-tool sign -inFile libcxxabi_shim.so -outFile dep_signed/libcxxabi_shim.so -selfSign 1

# 宿主探针必须导出 __clear_cache（compiler-rt 符号需要宿主提供）
clang -o dlopen_probe dlopen_probe.c -ldl -Wl,-E
LD_LIBRARY_PATH=dep_signed ./dlopen_probe ./libjvm_selfsign.so
```

**E2 实测对照（2026-10-23，`mc-runtime-lab/docs/10-M1实施结果.md` §8）**

| 变体 | 结果 |
|---|---|
| 原始（无 `.codesign`） | ❌ FAIL `Permission denied` |
| `-selfSign 1`（依赖也 self-sign） | ✅ dlopen OK；`dlsym(JNI_CreateJavaVM)` 非空，地址 = `st_value + bias` 互证 |
| `-appCertFile/-profileFile`（debug 证书/profile） | ❌ FAIL `Permission denied`（ELF 代码签名**不认 HAP 证书/profile**） |
| 目标库已 self-sign + **依赖未签** | ❌ FAIL（依赖链必须逐个 self-sign；`LD_LIBRARY_PATH` 里 unsigned 版本会抢先命中） |
| 宿主未导出 `__clear_cache` | ❌ `symbol not found`；用 `-Wl,-E` 导出后通过 |

⚠️ **适用边界（E2 判读，别当万能）**：
- self-sign 在 **`develop_tools_debug_hap` 域 + 用户存储**下被接受；**应用数据目录（`/tmp`）仍不能 dlopen**。
- **普通 HAP 应用域未验证** —— 决定性实验是把库放进 HAP 的 `libs/` 随包安装后再测。
- 复现脚本（另一项目）：`Common/mc-runtime-lab/tools/05-签名并dlopen测试.sh`（29 行）。

> 结论：self-sign 路线**已验证可行**，但"纯 dlopen"仍需宿主配合（导出 `__clear_cache`）且受应用域限制；
> 首次在自己项目用，必须复跑 E2 五条对照再写进构建脚本。

## 4. 验证清单（原生项目每次出包都过一遍）

```sh
readelf -S out/libfoo.so | grep -i codesign     # 期望有 .codesign
<clt>/sdk/default/openharmony/toolchains/lib/binary-sign-tool display-sign -inFile out/libfoo.so
# 然后在目标设备/应用中实际 dlopen 一次
```
